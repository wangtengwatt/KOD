# KOD 全平台功能等价与单一源码设计

**日期：** 2026-08-18  
**状态：** 已完成分章节确认，等待书面规格最终审阅  
**业务源码基准：** `D:\watt\kod` 当前工作区  
**目标平台：** Windows/macOS/Linux 桌面端、Android、iOS 17+（iPhone 与 iPad）

## 1. 目标

以 `D:\watt\kod` 为唯一业务源码上游，把当前正式用户功能以“结果等价”的方式交付到桌面、Android 和 iOS。三端共享业务逻辑、数据模型、接口契约和验收用例；平台差异只存在于原生外壳、系统交互和安全适配层。

“功能等价”表示同一用户能在三端找到同一正式功能、得到相同业务结果、看到相同云端数据，并能在另一设备继续任务。它不要求 iOS 在本地复现 Electron、任意命令执行、桌面托盘或全局快捷键的底层实现。

最终成功标准：功能目录中的每一项正式用户功能都通过桌面、iPhone、iPad 和 Android 的入口、结果、同步、错误恢复和权限验收，没有依赖三份人工复制的业务源码。

## 2. 事实与问题定义

设计时工作区包含三份已实质分叉的客户端工程：

- `kod` 位于主线 `suanlizhongxin_KOD`，设计时 HEAD 为 `9bce12b`。
- `KOD-iOS` 基于较早的 `5346c45`，同时含有大量未提交的 iOS、认证、同步和云沙箱适配。
- `kod-android` 位于独立 Android 分支，和 `kod/src` 已有约 247 个源码文件差异。

现有移动平台实现还明确缺失或限制知识库、会话附件 RAG、桌宠、沙箱、MCP stdio、Skills 脚本执行、桌面 OAuth、本地复杂文件解析等能力。仅复制页面或显示入口不能称为功能完成。

因此，本项目解决的核心问题不是“继续把桌面文件复制到手机工程”，而是建立一个共享产品内核、稳定的平台契约和可验证的云端执行面。

## 3. 已确认的产品边界

### 3.1 纳入范围

- KAI/KOD 统一身份、令牌刷新、账号删除和设备会话。
- 聊天、会话、消息、附件、联网搜索、模型选择和提供商配置。
- 任务、工具调用、云沙箱、流式输出、恢复与取消。
- 图片生成、视频生成及跨设备历史。
- 知识库、文档解析、索引、RAG 和会话附件 RAG。
- MCP、Skills、权限确认、安装配置和执行。
- 搭档、模型配置、技能配置、应用设置及同步。
- 算力中心的买家与卖家正式功能、资产、订单、收益和钱包。
- StoreKit 2、Google Play Billing、服务端权益账本和恢复购买。
- 通知、分享、文件选择、安全存储等平台原生能力。

### 3.2 不纳入正式客户端

- `dev/*` 调试页面、测试入口和构建工具。
- 服务端运营与平台管理员后台；管理员继续使用独立 Web 后台。
- 在 iOS 强行伪造桌面托盘、桌宠悬浮窗、窗口控制或全局快捷键。
- 在移动设备本地运行不受信任的任意脚本或直接暴露宿主机能力。

### 3.3 平台专属等价规则

- 桌面托盘、窗口控制和全局快捷键属于桌面增强功能，不计作移动端缺项。
- 桌宠在移动端用应用内入口和系统通知表达状态，不创建系统级常驻悬浮进程。
- 桌面本地文件、命令、MCP stdio、Skills 和 RAG 在移动端通过云端任务协议提供相同业务结果。
- 三端页面使用同一响应式业务组件；仅导航模式、触控尺寸、安全区、分享、通知和支付桥接允许不同。

## 4. 方案选择

### 4.1 评估过的方案

1. **单仓库直接构建三端。** 漂移最少，但不保留独立的 iOS 与 Android 发布仓库。
2. **主源码加轻量发布仓库。** `kod` 保存业务源码；iOS 与 Android 仓库只保存原生发布资产并锁定一个上游提交。
3. **三份完整源码自动合并。** 短期改动少，但持续产生冲突和无法证明的功能漂移。

### 4.2 选择

采用方案 2。

- `kod` 是唯一业务源码、共享 UI、TypeScript 平台适配、接口契约和测试的上游。
- `KOD-iOS` 只保留 Capacitor iOS 工程、Swift 插件、权限、Entitlements、StoreKit、签名和 App Store 配置。
- `kod-android` 只保留 Android 工程、Kotlin 插件、权限、Keystore 和 Play 配置。
- 两个移动发布仓库用不可变提交标识锁定同一个 `kod` 版本。
- CI 检查两个发布仓库的业务提交哈希；不一致时禁止发布。
- 现有移动端独有改动先逐项审计和迁回 `kod`，通过测试后再去除重复业务源码。不得覆盖或丢弃用户已有的未提交改动。

## 5. 系统架构

### 5.1 客户端产品内核

`kod` 继续使用现有 Electron、React、TypeScript、TanStack Router、Jotai/Zustand、React Query 和 Capacitor 技术栈。共享代码按职责划分：

- **领域与契约：** 消息、任务、媒体、知识库、Skills、MCP、算力、订单、权益和同步实体。
- **共享业务 UI：** 三端共同使用的正式页面、状态机和错误展示。
- **平台接口：** 安全存储、文件、分享、通知、支付、深链、更新和系统信息。
- **平台实现：** Electron 实现、Capacitor 实现和测试实现。
- **同步客户端：** Outbox、增量同步、冲突合并、游标和本地缓存。
- **任务客户端：** 幂等提交、事件流、断线恢复、取消和后台通知。

### 5.2 移动发布仓库

移动仓库不接受业务页面、领域模型或业务 API 的直接修改。其职责限定为：

- 原生工程和 Capacitor 插件接线。
- iOS Keychain、Android Keystore、通知、分享和文件选择。
- StoreKit 2 与 Google Play Billing 原生桥接。
- Bundle/Application ID、权限、签名、隐私清单和商店元数据。
- 从锁定的 `kod` 提交生成 Web 资产并执行原生同步。

### 5.3 云端控制面

`kod-ai-portal` 作为控制面，逐步承载或调用以下独立模块：

- KAI/KOD 身份和设备会话。
- 同步 API 与变更日志。
- 对象存储授权和数据保留策略。
- 凭据保险库与模型调用代理。
- 任务 API、队列、事件日志和调度。
- 算力市场、订单、钱包、权益和支付验证。
- 审计、举报、内容治理和通知。

模块通过版本化接口和事件通信；不得让客户端直接依赖内部数据库表或 H100 节点地址。

### 5.4 执行面

- H100 节点运行经过审核、版本固定的模型推理服务，并通过模型网关暴露能力。
- MCP、Skills、命令和文件工具运行在独立微虚拟机沙箱，不与 H100 推理进程共享安全边界。
- 普通用户任务不直接获得 GPU 驱动、宿主机文件、Docker Socket 或集群凭据。
- 需要自定义 GPU 环境时只允许运营方签名、扫描和批准的镜像。
- 每次任务的执行容器在任务结束后立即销毁。

## 6. 功能目录与等价验收

建立机器可读的功能目录。每个条目至少包含：

- 稳定功能 ID 和中文名称。
- 正式入口和需要的用户角色。
- 共享业务组件和服务端能力。
- 桌面、iPhone、iPad、Android 的执行方式。
- 所需系统权限和审核说明。
- E2E 用例、离线用例、恢复用例和当前完成状态。

功能状态仅允许：`not-started`、`in-progress`、`blocked-external`、`verified`。只有四个目标形态的入口、结果、同步和错误恢复均通过，才可标记 `verified`。内部调试功能不进入该目录。

## 7. 身份与凭据

### 7.1 身份流程

- KAI/KOD 登录成功后签发短期 Access Token 和单次轮换 Refresh Token。
- 原生端把令牌存入 Keychain 或 Keystore；桌面使用系统安全存储。
- 同一进程只允许一个刷新请求，其余受保护请求等待结果。
- 刷新成功后重放一次原请求；再次返回未授权则清理会话。
- 刷新失败时记录安全返回路径，进入 KOD AI 登录，成功后返回原功能。
- 删除账号时撤销全部设备会话和刷新令牌。

### 7.2 第三方凭据

- API Key 和 OAuth 凭据可以跨设备使用，但数据库不保存明文。
- 服务端使用 KMS 信封加密；每个密钥记录归属、用途、版本和撤销状态。
- 客户端只获取脱敏元数据，本地缓存进入 Keychain/Keystore。
- 云沙箱不能读取密钥；模型和外部服务调用必须经过凭据代理。
- 导出数据、日志、崩溃报告和审计事件不得包含凭据明文。

## 8. 跨设备同步

### 8.1 持久实体

长期同步直到用户删除：

- 聊天、消息和会话设置。
- 任务定义、状态、事件摘要和用户保存的产物。
- 图片与视频生成历史。
- 模型、提供商、搭档和技能配置。
- 知识库元数据、保存文档和索引版本。
- 应用偏好、设备可用性和通知状态。
- 算力资产、订单、权益和账本视图。

### 8.2 协议

- 客户端变更先写入本地 Outbox，再携带幂等键、实体版本和设备 ID 上传。
- 服务端返回单调同步游标；客户端按游标拉取增量变更和删除墓碑。
- 消息、任务事件和审计记录使用追加模型；允许显式修订，不覆盖历史事实。
- 一般设置冲突按服务端接收顺序解决，并保留最近修改设备和时间。
- 余额、订单、支付、权益和任务最终状态由服务端权威状态机决定，客户端不能用本地时间覆盖。
- 同步 API 需要版本化，旧客户端至少在一个受支持发布周期内可读取新数据。

### 8.3 数据保留

- 用户主动保存的文件和产物长期同步，直到用户删除。
- 沙箱临时文件默认保留 7 天，随后由生命周期策略删除。
- 用户删除账户后立即阻止访问，并异步清除对象存储副本、索引和缓存；审计留存只保留法规或安全所需的最小脱敏记录。

## 9. 任务与流式回传

- 创建任务必须携带客户端生成的幂等键；重复提交返回同一任务。
- 任务队列保存明确状态：`queued`、`running`、`waiting-for-approval`、`succeeded`、`failed`、`cancelled`、`expired`。
- Worker 把输出、工具调用、审批请求、计量和终态写入有序事件日志。
- 客户端使用事件序号去重；断线后从最后确认序号恢复，不重新创建任务。
- 应用进入后台后停止依赖常驻连接，改由 APNs/FCM 通知审批和终态；回到前台再增量拉取。
- 取消是幂等操作；如果 Worker 已结束，返回现有终态。
- 计量和扣费依据服务端已确认事件，不依据客户端是否收到流式内容。

## 10. 文件、知识库、MCP 与 Skills

- 文件通过短期签名 URL 上传对象存储；文件元数据和内容哈希进入同步实体。
- 文档解析、切分、嵌入和索引在云端执行，索引版本与源文件版本绑定。
- MCP 和 Skills 使用统一能力清单，声明文件读取、文件写入、网络域名、凭据别名、命令和外部副作用。
- 高风险能力每次执行都需要明确确认；低风险能力可由用户设置会话级授权。
- 安装前执行签名校验、静态扫描和权限预览；运行时执行网络出口与资源限制。
- 市场内容支持审核、举报、屏蔽、下架和版本撤销。

## 11. 算力、钱包与应用内购买

- 算力市场的买家、卖家、资产、订单和收益属于正式客户端功能；管理员功能留在独立 Web 后台。
- 任何扣费、结算、退款和权益发放都写入服务端不可变账本，并使用业务幂等键。
- iOS 内购买数字权益使用 StoreKit 2；中国大陆构建不显示外部充值按钮或诱导链接。
- Android 对应商品使用 Google Play Billing。
- Apple/Google 交易在设备端完成平台校验后，还必须提交服务端验证并关联 KOD 用户。
- iOS 服务端接入 App Store Server API 和 App Store Server Notifications V2，不新增对弃用 `verifyReceipt` 的依赖。
- 消耗型算力时数由服务端账本维护，不能仅依赖 StoreKit `currentEntitlements`；通过 IAP 购买的点数不设置到期日。
- 跨平台购买映射到同一权益类型，但各平台展示和购买入口遵守对应商店规则。

## 12. 安全与审计

- 沙箱使用非 root、只读基础镜像、临时可写层、资源配额、系统调用限制和网络出口白名单。
- 用户之间不共享可写卷、进程命名空间、服务账号或凭据。
- 所有工具副作用、权限确认、任务调度、模型调用、计量、订单和管理员操作写入追加审计日志。
- 日志在写入前脱敏，并限制查询权限和保留期。
- API 使用统一错误分类：认证、权限、冲突、限流、可重试依赖失败、永久业务失败和未知服务错误。
- 仅幂等操作自动重试；非幂等副作用必须先查询幂等记录。
- 支付通知、队列事件和同步变更允许至少一次投递，消费者必须去重。
- 数据库、对象存储和账本建立备份与恢复演练；账本恢复必须能证明借贷平衡。

## 13. 错误恢复和用户体验

- 认证错误自动尝试一次协调后的刷新；失败才要求重新登录。
- 网络错误保留本地草稿和 Outbox，显示离线状态而不是删除用户操作。
- 任务错误展示可理解的阶段、错误码、是否扣费和可执行的重试动作。
- 流式中断先尝试按序号续传；服务端确认任务不存在时才允许创建新任务。
- 文件上传支持分片或可恢复上传；内容哈希相同的完成文件不重复上传。
- 权限被拒绝时显示具体能力和原因，不用通用“失败”替代。
- 支付结果处于未知状态时只允许“刷新订单状态”，禁止再次扣款。

## 14. 分阶段实施

本设计是总纲。由于范围包含多个独立子系统，实施必须拆成以下可独立验收的子项目，每个子项目建立自己的计划和评审门槛：

1. **源码统一与功能目录：** 审计三份工程、迁移独有改动、建立上游锁定和构建矩阵。
2. **身份、凭据与同步：** KAI/KOD 会话、KMS 凭据保险库、Outbox 和增量同步。
3. **聊天、任务与媒体：** 跨设备聊天、任务、图片、视频和后台通知。
4. **云执行与知识能力：** 任务队列、事件流、微虚拟机沙箱、MCP、Skills、知识库和 RAG。
5. **算力商业闭环：** 买卖双方流程、钱包、不可变账本、StoreKit 2 和 Google Play Billing。
6. **全平台发布：** 性能、安全、隐私、商店材料、签名、TestFlight 和发布回归。

每个阶段同时生成桌面、Android 和 iOS 可测试版本。只有全部阶段通过后，产品才可以声明“所有正式客户端功能已复刻”。

## 15. 测试策略

### 15.1 自动化层级

- 领域状态机、合并规则、权限策略和账本使用单元测试。
- 客户端与服务端使用共享 Schema 做 API 契约测试。
- 数据库、Redis、对象存储、队列、KMS 适配和支付通知使用集成测试。
- 同一功能脚本分别运行桌面 WebDriver、Android 和 iOS E2E。
- 沙箱执行逃逸、越权、网络出口、资源耗尽和密钥读取负向测试。

### 15.2 必测场景

- 新设备登录后增量恢复全量用户数据。
- 两台设备离线修改后重新联网并按规则合并。
- Access Token 失效、刷新轮换、刷新失败登录返回。
- 流式任务断线、后台、跨设备接管、取消和重复提交。
- 上传中断、临时文件过期、保存产物和账户删除。
- 支付成功、待定、退款、撤销、通知重复和客户端重装恢复。
- 并发购买、扣费、卖家结算和账本平衡。
- MCP/Skill 权限允许、拒绝、撤销、版本下架和恶意输入。

### 15.3 发布门槛

- 功能目录没有目标版本内的 `not-started` 或 `in-progress` 条目。
- 桌面、iPhone、iPad 和 Android 的共享 E2E 全部通过。
- iOS 与 Android 发布仓库锁定同一个 `kod` 业务提交。
- 类型检查、lint、单元测试、集成测试、原生构建和依赖安全扫描通过。
- StoreKit Sandbox、App Store Server Notifications V2 和 Google Play 测试轨道通过。
- 发布包不包含调试入口、测试凭据、外部 iOS 数字充值入口或未声明权限。

## 16. 发布与外部阻塞

Windows 可以完成共享源码开发、Web/Electron 构建、Android 构建、Capacitor iOS 同步和 iOS 源码检查，但不能生成、签名或上传真实 TestFlight 归档。

进入 TestFlight 前必须具备：

- Apple Developer Program 团队和 App Store Connect 应用记录。
- macOS、兼容 Xcode、有效签名证书和 Provisioning Profile。
- 正式 Bundle ID、StoreKit 商品、隐私政策、支持页面和审核账号。
- App 隐私声明、权限用途说明、出口合规和审核备注。

这些是外部发布条件，不得把缺少 Apple 账号或 macOS 误标为代码完成，也不得通过隐藏支付或功能规避审核。

## 17. 开源边界

- 业务源码、客户端壳、接口 Schema、迁移和测试可以开源。
- 生产密钥、KMS 主密钥、签名证书、Provisioning Profile、Keystore、商店密钥和集群凭据不得进入仓库。
- 示例配置只包含变量名和本地开发默认值，不包含可用生产凭据。
- 构建流程支持开发者替换服务端地址和自有签名，但官方客户端只信任官方生产配置。

## 19. 决策摘要

- `kod` 是唯一业务源码上游。
- iOS 和 Android 是轻量原生发布仓库，不再人工复制业务代码。
- 移动端追求业务结果等价，桌面专属系统交互使用移动端等价入口。
- 正式任务统一走云端控制面与隔离执行面。
- 保存数据跨设备长期同步；临时文件保留 7 天；任务容器立即销毁。
- 第三方凭据使用 KMS 信封加密和凭据代理。
- 正式用户功能全量纳入，开发、测试和运营后台不进入客户端。
- 全项目分六个子项目实施，每阶段同时验证三端。
