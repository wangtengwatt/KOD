# KOD 微信小程序全功能等价设计

- **日期：** 2026-08-19
- **状态：** 分章节设计已确认，提交书面规格供最终审阅
- **业务源码基准：** `D:\watt\kod`
- **目标客户端：** 微信小程序
- **目标分支：** `xcx_KOD`
- **关联总纲：** `docs/superpowers/specs/2026-08-18-cross-platform-feature-parity-design.md`

## 1. 目标与完成定义

以 `kod` 客户端正式源码为功能事实来源，在微信小程序中复刻全部正式用户业务能力。小程序需要提供同一用户可发现的入口、等价的业务结果、相同的云端数据、可恢复的错误路径和跨设备连续性。

“全功能等价”不表示在微信进程内照搬 Electron、Node.js、桌面文件系统或本地任意命令执行。无法在小程序安全模型内原样运行的能力，必须迁移到受控云端，并在小程序中提供相同业务结果、审批流程和结果制品。

机器可读功能目录允许以下终态：

- `verified`：小程序入口、结果、同步、恢复和权限测试全部通过。
- `verified-cloud-equivalent`：桌面本地能力已用云端受控能力实现业务结果等价，并通过专项安全测试。
- `excluded-approved`：仅限开发、测试、运营后台或无业务结果的桌面系统增强，且排除原因经过明确批准。
- `blocked-external`：代码与可离线验证部分完成，但真实发布受外部账号、资质或凭据阻塞；该状态不允许对外宣称已正式上线。

“客户端功能复刻完成”要求所有不受外部条件影响的条目均为 `verified`、`verified-cloud-equivalent` 或 `excluded-approved`，且每个 `blocked-external` 条目的代码、模拟验证证据和唯一外部阻塞均已明确记录。“正式上线完成”则要求功能目录中不存在 `blocked-external`。

## 2. 源码事实与边界

### 2.1 功能事实来源

功能事实以 `D:\watt\kod` 的正式路由、组件、领域类型、Store、服务适配器和测试为准。其他仓库用于补充服务能力或历史实现，不得反向成为小程序业务源码的长期分叉：

- `kod`：Electron + React + TypeScript 正式客户端及唯一业务源码上游。
- `kod-ai-portal`：Mini BFF、同步、聊天、媒体、算力、钱包和控制面服务的承载位置。
- `Identity`：微信代码交换、KAI/KOD 账户绑定、令牌轮换与设备会话。
- `kod-web`、`kod-android`、`KOD-iOS`：仅作为行为审计和平台适配参考，不复制成第四份业务实现。

### 2.2 纳入范围

- KAI/KOD 统一身份、微信一键登录、既有账户绑定、邮箱验证码回退、设备会话和账号删除。
- 对话、会话、消息、流式响应、停止、重试、编辑、引用、分叉、搜索和分享。
- 模型、提供商、KOD Relay、联网搜索、解析器、附件、文件和会话附件 RAG。
- 任务、工具调用、审批、云工作区、云沙箱、后台恢复、取消和结果制品。
- 图片生成、视频生成、参考素材、参数、进度、历史、保存和分享。
- 知识库、文档解析、切分、索引、RAG、MCP、Skills 和 Copilots。
- 算力中心买方与卖方正式功能、资产、预约、订单、礼赠、履约、收益、结算和钱包。
- 设置、主题、语言、通知、隐私、日志、关于、设备管理和跨端同步。

### 2.3 不纳入小程序正式客户端

- `dev/*`、内部测试页、构建工具和调试开关。
- 服务端运营、审核、财务复核和平台管理员后台。
- Electron 托盘、窗口控制、全局快捷键、桌面悬浮宠物和系统级常驻覆盖层。
- 在微信设备上运行任意本机脚本、MCP stdio、Node.js 子进程、本地 SQLite RAG 或暴露宿主文件系统。

上述最后两类只有在不存在正式用户业务结果时才可排除；存在业务结果的必须按云端等价规则实现。

## 3. 方案选择

评估过三种方案：

1. **微信原生 WXML/WXSS 全量重写。** 平台贴合最好，但会形成独立业务实现，长期漂移成本最高。
2. **WebView 包装现有 Web 客户端。** 初始速度快，但登录、支付、文件、审核、性能和平台交互受限，无法满足正式小程序交付标准。
3. **共享 TypeScript 产品内核 + Taro/React 小程序视图 + 云端 BFF。** 可复用领域模型和协议，同时让页面、权限和生命周期遵守微信小程序模型。

采用方案 3。

- 复用纯 TypeScript 领域类型、Schema、状态机、校验、错误分类和协议测试。
- 小程序页面与组件使用 Taro/React 重新实现，不直接复用 Mantine、MUI、DOM、Electron IPC、Node.js、IndexedDB 或本地 SQLite 代码。
- 所有敏感调用、长任务、模型代理、支付裁决和跨端同步经 Mini BFF。
- 微信适配只存在于小程序外壳和平台端口，不进入共享领域内核。

## 4. 仓库与模块架构

### 4.1 `kod` 客户端上游

规划在 `kod` 内形成以下边界：

```text
kod/
  packages/
    contracts/       # 版本化 Schema、事件、错误和 API 类型
    client-core/     # 纯 TS 领域逻辑、状态机、同步与恢复规则
  apps/
    wechat-mini/     # Taro/React 页面、组件和微信平台适配
  src/               # 现有桌面客户端；逐步消费共享 contracts/core
```

`packages/contracts` 不依赖 React、Taro、Electron 或具体传输库。`packages/client-core` 只依赖 contracts 和可注入端口。`apps/wechat-mini` 负责页面、导航、微信生命周期、权限、文件、分享、通知和支付桥接。

### 4.2 Mini BFF 与控制面

`kod-ai-portal` 增加版本化 Mini BFF，承担：

- 微信会话交换、KOD 账户绑定、访问控制和设备会话。
- API 聚合、速率限制、幂等、审计、错误归一化和功能开关。
- 消息事件、任务事件、同步游标、文件上传票据和媒体进度网关。
- 模型供应商代理、联网搜索、内容解析和凭据保险库访问。
- 算力、订单、钱包、支付、库存和履约的服务端权威操作。

客户端不得直接依赖内部数据库表、队列主题、对象存储主密钥、模型供应商密钥或计算节点地址。

### 4.3 云端执行面

- RAG、文档解析、MCP、Skills、命令和文件工具运行在隔离 Worker/沙箱。
- 沙箱使用最小权限、临时工作区、资源限额、网络出口策略和短期任务凭据。
- 高风险工具先写入审批事件，只有收到匹配任务与版本的明确批准后才能继续。
- 任务输出、审批、计量和终态写入有序事件日志；客户端只消费事件和制品。
- 模型推理节点与任意工具执行不共享安全边界。

## 5. 小程序信息架构

底部固定五个一级 Tab：

1. **对话**：会话列表、聊天页、模型/搜索/附件入口和消息操作。
2. **任务**：任务列表、任务详情、审批、云工作区和结果制品。
3. **创作**：图片、视频、生成历史和媒体详情。
4. **算力**：市场、资产、订单、卖家、收益和钱包。
5. **我的**：账户、安全、知识、MCP、Skills、Copilots、模型与全局设置。

桌面路由到小程序入口的主要映射：

| 桌面正式入口 | 小程序入口 | 等价说明 |
| --- | --- | --- |
| `/`、`/session/$sessionId` | 对话 / 会话详情 | 保留消息与会话全部正式操作 |
| `/task`、任务详情 | 任务 / 任务详情 | 本地工具改为云任务和审批 |
| `/image-creator` | 创作 / 图片 | 长任务后台化 |
| `/video-creator` | 创作 / 视频 | 长任务后台化 |
| `/compute-center` | 算力 | 买卖双方与资金相关功能完整保留 |
| `/copilots` | 我的 / Copilots | 也可从对话创建页快捷进入 |

| `/guide`、`/about` | 我的 / 帮助与关于 | 使用小程序页面实现 |

### 6.5 我的

## 7. 核心契约与权威边界

### 7.1 通用写入信封

所有可产生副作用的请求至少携带：

- `requestId`：客户端生成、跨重试保持不变。
- `idempotencyKey`：服务端去重键。
- `deviceId`：设备会话标识，不使用可伪造的硬件唯一号。
- `entityVersion`：需要乐观并发控制时提供。
- `clientContractVersion`：用于兼容与灰度。

服务端响应包含稳定业务 `errorCode`、可执行用户提示和 `traceId`。客户端不解析内部异常字符串决定流程。

### 7.2 事件协议

消息流、任务、媒体和文件处理统一使用有序事件语义：

- 每个聚合拥有稳定 ID 和单调 `sequence`。
- 客户端保存最后确认序号，重连时从该序号之后恢复。
- 重复事件按 ID/sequence 去重，缺口由服务端事件日志补齐。
- 小程序默认使用 WebSocket 事件适配器；连接不可用时退化为游标增量查询。
- 传输方式可以替换，但事件顺序、幂等与终态语义不可变化。

### 7.3 服务端唯一权威状态

以下数据永远不接受客户端“最后写入获胜”：

- 余额、账本、支付、订单、退款、权益和结算。
- 库存预占、履约和算力资产。
- 任务、媒体生成和文件安全处理的最终状态。
- 审批审计、账号删除状态和设备撤销状态。

客户端可以乐观展示请求已受理，但必须等待权威事件后才能展示业务成功。

## 8. 身份、会话与凭据

### 8.1 登录和绑定

1. 小程序调用 `wx.login` 获取临时代码。
2. Mini BFF 与微信接口交换身份，并向 Identity 请求一次性绑定票据。
3. 已绑定用户直接建立 KOD 会话；未绑定用户选择绑定既有 KAI/KOD 账户或创建允许的新账户流程。
4. 微信链路不可用时使用邮箱验证码回退；两种方式最终映射到同一个 KOD 用户 ID。

### 8.2 令牌策略

- Access Token 短效并仅保存在运行内存。
- 小程序持久层只保存不透明、设备绑定、可轮换和可撤销的 Refresh Handle。
- 同一设备同时只执行一个刷新请求，其他请求等待结果。
- 刷新成功后最多重放一次具有幂等保护的原请求。
- 刷新失败时保留草稿和安全返回路径，清理会话后重新登录。
- 删除账户或撤销设备时立即使对应 Handle 失效。

### 8.3 密钥边界

- 模型 API Key、支付私钥、对象存储主密钥、SSH/节点凭据和 KMS 密钥不进入小程序。
- 用户自带第三方密钥由服务端加密托管；客户端只显示脱敏元数据和撤销状态。
- 日志、分享、导出、错误上报和任务制品不得包含凭据明文。

## 9. 关键数据流

### 9.1 对话

小程序先写草稿/Outbox 和幂等键，经 BFF 完成鉴权、额度和附件权限校验，再由模型代理调用供应商。流式事件按序写入服务端日志并回传；小程序断线后使用 sequence 续传。供应商密钥永不下发。

### 9.2 文件与知识库

小程序请求短期上传票据，按摘要和分片上传对象存储。服务端依次执行所有权校验、病毒/内容扫描、解析、切分和索引，最后只向客户端返回 `fileId`、版本和处理状态。业务数据不依赖微信临时绝对路径。

### 9.3 云任务

创建任务后由队列、事件日志和隔离 Worker 驱动。敏感工具产生审批事件；用户批准、拒绝或取消均是幂等命令。结果以制品和权威终态返回，微信进程退出不影响任务执行。

### 9.4 支付与履约

服务端锁价、预占库存并创建订单，再签发微信支付参数。客户端支付页面结果只表示交互完成，BFF 必须验签渠道回调并按交易号去重，随后写入账本、发放权益和触发履约。支付未知态只查询原订单，禁止新建重复订单。

### 9.5 增量同步

客户端变更先进入 Outbox，再携带实体版本和设备 ID 上行；服务端返回单调游标、增量变更和删除墓碑。草稿与普通设置按领域合并规则处理，资金与任务终态只接受服务端事件。

## 10. 异常处理与恢复

统一恢复顺序为：**检测 → 保全 → 对账 → 恢复**。

- **登录过期：** single-flight 刷新；只重放一次幂等请求；失败后重新登录并返回原路径。
- **离线/超时：** 保留草稿和 Outbox；超时视为结果未知；恢复后先按 requestId 对账。
- **流式中断：** 保留已显示内容和 sequence；续传同一流，不创建第二条消息或重复计费。
- **上传中断：** 保存上传会话、摘要和分片清单；重新签票后跳过已确认分片。
- **后台任务：** 保存 taskId 与游标；回前台拉取权威状态，不用端上超时推断失败。
- **支付未知态：** 冻结重复支付动作，仅刷新原订单；明确未支付或关闭后才允许重新支付。
- **账号删除：** 身份复核后立即撤销全部设备会话，再异步删除或合规匿名化数据并提供可核验状态。

统一错误分类为 `AUTH`、`PERMISSION`、`CONFLICT`、`RATE_LIMIT`、`DEPENDENCY`、`BUSINESS_RULE` 和 `UNKNOWN`。只有幂等且在重试预算内的操作可以自动重试。

## 11. 安全与隐私

- Mini BFF 执行 RBAC、租户/资源所有权校验、限流、幂等和审计；不能仅依赖页面是否展示按钮。
- 文件、知识库、任务、订单和卖家资源逐资源授权，防止跨用户 ID 枚举。
- 沙箱非 root、隔离工作区、最小权限、资源配额、网络出口策略和短期凭据。
- 支付回调、队列事件和同步变更按至少一次投递设计，消费者必须去重。
- 登录、绑定、设备撤销、工具审批、资金、账号删除和管理操作写入追加审计日志。
- 日志和遥测在写入前脱敏，按用途限定访问和保留期。
- 数据最少采集；权限按动作申请；隐私声明、数据导出、删除和保留规则形成闭环。
- 正式域名使用 TLS，并在发布前按当期微信平台要求核验合法域名、隐私声明和权限用途。

三条不可越过的红线：

1. 小程序不直连模型供应商、数据库、支付回调或云沙箱。
2. 小程序不保存供应商密钥、支付私钥、SSH 凭据或长期裸令牌。
3. 客户端成功页面不能改变余额、订单、权益或任务最终状态。

## 12. 功能目录与追踪

P0 建立机器可读功能目录。每个条目至少包含：

- 稳定功能 ID、名称、用户角色和源码证据。
- 桌面入口、小程序入口和云端等价说明。
- 共享领域模块、BFF 契约、权限和数据权威方。
- 正常、离线、恢复、越权和真机测试证据。
- 当前状态、外部阻塞、责任子项目和审核说明。

功能目录是“所有功能”声明的唯一核销清单。页面数量、路由数量或构建成功不能代替逐项功能证据。

## 13. 测试策略

### 13.1 自动化层级

- **共享核心：** 领域状态机、合并规则、幂等、错误映射和权限策略的单元/性质测试。
- **契约：** JSON Schema/OpenAPI 兼容测试、黄金样例和消费者契约测试。
- **BFF 集成：** 数据库、队列、对象存储、回调、账本和外部适配器集成测试。
- **小程序：** Taro 页面/组件测试、微信开发工具自动化和端到端流程。
- **真机：** iOS/Android 微信、弱网、前后台、权限、文件、相册、分享和长任务恢复。
- **安全：** 越权、ID 枚举、回调重放、幂等并发、恶意文件、沙箱逃逸、密钥扫描和依赖扫描。
- **资金：** 并发库存、重复回调、支付未知态、关闭/退款、账本平衡和权益重复发放。

### 13.2 发布证据

每个需求必须能追踪到契约、实现提交、自动化用例、真机记录和功能目录状态。性能预算与微信平台约束在 P0 记录基线，在 P6 使用当期规则重新核验；本设计不硬编码可能变化的平台数值。

## 14. 分阶段交付

本设计是全项目总纲，范围过大，不得用一个超长实施计划一次性开工。P0–P6 每个子项目都必须单独执行“规格 → 书面审阅 → 实施计划 → 测试驱动实现 → 验收”流程。

### P0：共享契约与小程序骨架

统一功能目录、Schema/OpenAPI、共享状态机、Taro 五栏外壳、Mini BFF 基座、CI 和可复现构建。出口是桌面契约兼容、小程序开发工具/真机加载和基础 CI 证据。

### P1：身份、账户与增量同步

实现微信登录、KOD 绑定、邮箱回退、令牌轮换、设备管理、账号删除、Outbox、游标同步和基础“我的”。

### P2：对话、文件、搜索与 Copilots

实现会话/消息全生命周期、流式续传、模型/提供商、附件、分享、联网搜索、Copilots 和会话附件 RAG 接口。

### P3：任务、RAG、MCP、Skills 与云沙箱

实现任务状态机、审批、隔离工作区、知识库索引、MCP/Skills 云执行、后台恢复、通知和结果制品。P3 依赖 P2 的消息与文件协议。

### P4：图片与视频创作

实现图片/视频模型与参数、参考素材、长任务进度、失败重试、历史、预览、保存、分享和同步。P4 在 P1 后可与 P2/P3 并行。

### P5：算力、钱包、订单与支付

实现买卖双方、节点/商品、库存、履约、订单、礼赠、收益、结算、钱包账本、支付和回调。资金链路独立进行负向安全验收。

### P6：安全、性能、隐私与审核就绪

执行全功能差异核销、威胁模型、性能预算、可观测性、隐私声明、账号删除、全量真机回归、审核材料和回滚演练。

## 15. 发布闸门

正式候选版本必须连续满足：

1. 功能目录逐项为 `verified`、`verified-cloud-equivalent` 或获批的 `excluded-approved`；外部阻塞单独列示。
2. 构建、单元、契约、集成、小程序端到端和真机证据完整可追溯。
3. 安全、隐私、账号删除、审计、沙箱和资金负向测试通过。
4. 性能预算、合法域名、权限声明和当期微信平台规则完成重新核验。
5. 无未解决阻断级缺陷，审核材料、版本标识、监控和回滚方案齐备。

## 16. 外部阻塞与配置

当前没有企业微信小程序 AppID，也没有已关联的微信支付商户配置。因此可以完成：

- Taro 小程序源码、测试 AppID/本地构建适配和可替换环境配置。
- 微信登录、支付和回调的版本化接口契约与模拟适配测试。
- 支付幂等、验签适配边界、账本、未知态和履约的自动化验证。
- 微信开发工具和具备条件的测试环境验证。

以下工作必须等待用户提供相应账号和凭据：

- 企业主体能力、正式合法域名和正式隐私配置联调。
- 真实微信登录身份链路的生产验收。
- 真实微信支付下单、签名、回调和商户结算验收。
- 最终版本上传与微信审核提交。

生产凭据、私钥和证书不得提交到 Git；仓库只保存环境变量名、示例配置和校验脚本。

## 17. GPL 与发布边界

当前 `kod` 根目录 `LICENSE` 为 GNU GPL v3。本项目基于该客户端源码开发小程序，必须保留版权与许可证声明，并在分发衍生客户端时履行对应源代码提供义务。具体发布方式在 P6 由法律/合规人员复核，但不得以闭源打包、删除声明或混入生产密钥规避许可证要求。

服务端与客户端通过版本化公开协议解耦；是否构成同一衍生作品以及不同服务模块的许可证范围需由法律审查最终确认。本设计不把法律判断替换为技术假设。

## 18. 已确认决策摘要

- `kod` 是唯一业务源码上游，不新建人工维护的第四份业务实现。
- 技术路线为共享 TypeScript 内核 + Taro/React 小程序 + Mini BFF。
- 一级导航固定为“对话 / 任务 / 创作 / 算力 / 我的”。
- 微信一键登录优先，绑定既有 KAI/KOD 账户，邮箱验证码回退。
- 桌面本地 RAG、MCP stdio、Skills 和命令执行迁移到隔离云端实现结果等价。
- 模型、支付、存储和节点密钥永不下发小程序。
- 消息、任务、媒体和文件处理使用有序事件与游标恢复。
- 资金、订单、权益、库存和任务最终状态由服务端唯一裁决。
- 全范围按 P0–P6 子项目推进，不因分期缩减功能范围。
- 交付目标是具备提交微信审核条件；真实提交和支付生产验收受企业 AppID 与商户配置阻塞。

## 19. 书面审阅后的下一步

用户审阅并批准本文件后，只为 P0 编写详细实施计划。P0 验收后再依次为 P1–P6 建立各自规格和计划；不得在总纲批准后跳过子项目设计与测试门槛直接批量实现全部功能。
