## Context

参见 [proposal.md](./proposal.md) 的动机。当前算力中心主要由三个超大文件承载：路由页面同时负责查询、权限、交互与渲染，卡时组件同时处理资产、转让和邀请业务，API 文件同时包含类型、请求细节与全部领域方法。Windows 桌面版、Web、Android 和 iOS 共用 renderer，因此一次不受约束的拆分可能同时影响四端。

本次设计受以下约束：现有用户界面、导航、角色叠加规则、后端接口、查询结果语义和业务流程保持不变；不修改后端或数据库；不引入新的运行时依赖或全局状态框架；自动化测试不得访问真实业务数据库；只有会造成登录失败、错误扣款、重复下单、敏感数据泄露、页面崩溃或永久加载的问题可以在本变更中随重构修复。

## Goals / Non-Goals

**Goals:**

- 建立按业务领域划分、单向依赖且可独立测试的算力中心客户端结构。
- 保留 `src/renderer/packages/computeCenter.ts` 的公开导出，使现有调用方可以渐进迁移。
- 用行为特征测试冻结现有界面、权限、API 契约、资产与订单关键流程。
- 统一查询键、操作状态、错误归类、结果未知处理与敏感数据清理方式。
- 让 Windows、Web、Android、iOS 继续共享 renderer 业务实现，并明确各端可执行的验证边界。
- 让后续产品缺陷可以作为独立 OpenSpec 变更处理，而不是混入结构重构。

**Non-Goals:**

- 不重新设计算力中心页面、文案、导航或业务规则。
- 不新增或调整后端接口、数据库表、字段、索引、管理员名单或资金规则。
- 不改动官网钱包、登录体系、零售站/节点选择、对话、生图和生视频流程。
- 不引入 Redux、Zustand 等新全局状态层，也不替换 React Query、Mantine、TanStack Router 或现有 Platform 抽象。
- 不承诺在 Windows 环境完成 iOS 原生编译、签名和真机验收；该部分由 macOS/Xcode 或 macOS CI 完成。

## Decisions

### 1. 采用“领域模块 + 兼容门面”的渐进式结构

路由入口 `src/renderer/routes/compute-center.tsx` 最终只承担页面骨架、身份上下文、一级导航和领域容错边界。路由私有目录按以下职责组织：

```text
src/renderer/routes/
├── compute-center.tsx
└── compute-center/
    ├── -components/       # 页面级共享展示组件
    ├── -hooks/            # 页面编排、操作控制与权限派生
    ├── -utils/            # 纯格式化和状态映射
    └── -features/
        ├── market/
        ├── card-hours/
        ├── assets/
        ├── purchases/
        ├── orders/
        ├── supplier/
        ├── notifications/
        └── admin/
```

每个 feature 对自己的查询组合、空态、加载态、错误态和交互负责，但不得直接访问其他 feature 的内部文件。跨领域共享的只读展示组件放入 `-components`，业务规则放入 `-hooks` 或 API 领域模块。路由文件目标控制在约 200–300 行；feature 文件在不损害可读性的前提下尽量不超过约 500 行，这些是维护性目标而非构建时硬限制。

API 层拆分为：

```text
src/renderer/packages/compute-center/
├── client.ts
├── queryKeys.ts
├── account.ts
├── marketplace.ts
├── cardHours.ts
├── packages.ts
├── reservations.ts
├── supplier.ts
├── notifications.ts
├── admin.ts
├── types.ts
└── index.ts
```

原 `src/renderer/packages/computeCenter.ts` 仅重导出新模块中的现有公开符号。迁移期间，旧路径和新路径必须返回相同类型和运行时行为；在全部调用方迁移并通过测试前不删除兼容门面。

选择该方案而不是一次性重写，是因为门面允许小步迁移、逐步回滚和逐领域验收。没有选择继续按“组件类型”拆文件，因为市场、资产和订单会继续横跨查询、交互与展示，无法形成清晰责任边界。没有选择微前端或独立 package，因为四端共享同一 renderer，额外发布边界会增加本阶段不必要的复杂度。

### 2. 以依赖方向约束模块边界

允许的依赖方向为：

```text
route shell → feature component → feature hook → domain API → shared client
                                      ↓
                              queryKeys / types / pure utils
```

API 层不得依赖 React、路由或 UI 组件；纯工具不得读取 store、浏览器全局或网络；feature 之间通过已有服务端数据或路由 shell 传入的最小接口协作。管理员、供应方和购买方权限都由现有账户响应派生，不创建第二套客户端权限源。

为避免循环依赖，所有公共类型从 `types.ts` 导出，查询键从 `queryKeys.ts` 导出，网络与错误规范化从 `client.ts` 导出。领域模块不得从兼容门面反向导入。

### 3. 冻结并集中 React Query 契约

把现有查询键集中到 `queryKeys.ts`，先用特征测试记录重构前的键形状和失效范围，再移动定义。领域 hook 只使用统一工厂，不在组件中创建临时字符串数组。迁移第一阶段保持现有缓存可见性和刷新语义；只有测试证明安全时，才把过宽的失效范围收窄到对应账户、商品、订单或设备键。

写操作成功后仍按现有流程刷新相关数据。写响应丢失或超时时，不重发资金/订单请求，而是执行只读刷新并提示“结果尚未确认，请核对资产或记录”。这能降低重复扣款和重复下单风险，但不能代替服务端幂等；若现有接口支持请求标识，则同一用户操作的人工确认重试复用原标识，若不支持则不伪造客户端幂等保证。

### 4. 用统一操作控制器收敛异步状态和防重

新增算力中心私有 `useComputeActionController`，按稳定的 action key（例如 `purchase-package:<productId>`、`reserve-gpu:<productId>:<slot>`）记录正在执行的操作。它负责：

- 同一 action key 未结束时拒绝第二次提交并保持按钮禁用；
- 在成功、业务失败、认证失败、网络失败、超时、用户取消和组件卸载时进入终态；
- 在组件卸载或退出登录时中止可安全取消的读请求并清理本地敏感状态；
- 把成功、失败和结果未知映射为现有三秒居中反馈；
- 阻止卸载后的状态更新。

读请求沿用网络层的取消能力。普通读取采用 30 秒客户端终止上限；文件材料读取/上传采用 120 秒上限。写请求达到终止上限时只结束 UI 加载并进入“结果未知”，不自动重试，也不向用户宣称失败。具体超时常量集中在 `client.ts`，便于测试和后续基于监控调整。

没有选择只依赖按钮 `disabled`，因为快速双击、多个入口和重新渲染仍可能并发提交。没有引入全局队列，因为不同商品或不同只读操作之间允许并行，全局串行会改变现有体验。

### 5. 卡时不足补足流程保持显式确认且最多续跑一次

统一卡时消耗入口接收“预计卡时”和原操作回调：余额足够时直接执行；卡时不足但人民币足够时展示精确缺口和兑换金额；用户确认后使用现有自动补足参数续跑原操作一次；用户取消时零写入；两种余额均不足时显示人民币缺口，并仅在用户确认后通过 Platform 外链能力打开官网钱包。

控制器为一次用户意图保存阶段状态，禁止“补足成功后原操作失败”触发第二次自动补足。此设计覆盖 GPU 套餐、Token 套餐、卡时转让以及所有现有卡时消费入口，但不扩展到新的业务类型。

### 6. 统一错误模型，但不改变服务端业务语义

`client.ts` 将异常归一为以下客户端类别：

- `validation`：本地输入不合法，不发请求；
- `business`：服务端明确拒绝，保留原业务错误码和安全文案；
- `auth`：登录过期或无权限，触发现有认证处理；
- `transport`：连接失败、超时、响应不可解析；
- `unknown`：程序错误或未识别响应。

归类只用于 UI 反馈、日志脱敏和重试决策，不改写服务端错误码。每个领域由 Error Boundary 隔离，单个领域崩溃时显示可刷新/重试的局部错误态，顶部账户区域、一级导航和其他领域仍可用。程序错误不得被伪装成业务失败；自动化测试要验证错误边界不会泄露原始响应或凭证。

### 7. 敏感凭证采用按需获取、内存短驻留和统一脱敏

Token 套餐完整 API Key 仅在用户主动显示时调用现有接口获取，保存在当前组件内存状态，不进入 React Query 持久缓存、localStorage、日志、通知文案或 URL。隐藏 Key、切换套餐/页面、退出登录和组件卸载都清空完整值。Base URL 可以正常显示和复制；API Key 的复制按钮只有在完整值成功获取后才可用。

共享脱敏函数处理 API Key、Bearer token、密码、身份证号、证件图片 URL、SSH 密码/私钥、上游密钥和数据库凭证。错误上报只允许包含错误类别、业务错误码、操作类别与脱敏上下文。测试夹具使用明确虚构的数据，不复制真实账户材料或密钥。

### 8. 通过现有 Platform 抽象维持四端一致

外链、剪贴板、文件选择/上传和平台识别继续通过现有 Platform/adapters 能力完成，feature 不直接调用 Electron、Capacitor 或仅浏览器可用 API。若现有 Platform 缺少某个必要方法，只在其现有接口和各平台实现中做最小补充，并为 Web fallback 增加测试；不在 feature 内做散落的平台判断。

验证分层如下：Windows 执行桌面生产构建和人工冒烟；Web 执行生产构建；Android 执行 renderer 构建、Capacitor sync，并在本机工具链可用时执行 Gradle 编译；iOS 在 Windows 上执行共享 renderer 构建和 Capacitor sync，原生编译、签名和真机验证交由 macOS/Xcode 或 macOS CI。任何未执行的原生步骤必须在交付报告中明确列出，不能写成“已验证”。

### 9. 先建立特征测试，再逐领域搬迁

测试分四层：

1. API 契约测试：固定路径、方法、请求体、鉴权头、解析结果与错误归类。
2. Hook/规则测试：权限派生、查询键、失效范围、卡时补足、操作防重、结果未知和敏感状态清理。
3. 组件特征测试：现有标签、导航、空态、角色入口、购买/预订确认、资产/订单交付信息和领域错误边界。
4. 安全回归测试：日志与错误脱敏、完整 Key 生命周期、卸载/退出后的清理。

所有测试以模拟 transport 和隔离 fixture 运行，默认网络未被 mock 时直接失败。真实环境冒烟脚本与自动测试分离，必须显式传入环境配置，且只允许登录状态、公开商品、账户资产等 GET/只读请求；脚本维护明确的只读路径白名单，遇到非白名单方法或路径立即终止。

没有选择依赖大量快照，因为超大快照难以判断业务回归；采用面向用户可见行为与请求契约的断言。没有把真实数据库作为集成测试环境，因为资金和订单写入不可接受且结果不可重复。

## Risks / Trade-offs

- [兼容门面可能长期存在并掩盖迁移遗漏] → 增加测试确保新旧入口导出一致，并在任务清单中逐个迁移内部调用；本变更不贸然删除门面。
- [移动代码时可能无意改变 React Query 缓存或刷新顺序] → 先记录查询键和失效行为，再移动定义；每迁移一个领域立即运行相关特征测试。
- [客户端防重不能彻底保证资金幂等] → 对结果未知的写操作禁止自动重试并先只读核对；服务端幂等作为后续独立变更评估。
- [固定超时会把慢写请求标记为结果未知] → 写请求不宣称失败、不自动重发，并提供核对入口；文件操作使用更长上限。
- [局部 Error Boundary 可能隐藏共因故障] → 顶层保留统一脱敏错误记录，局部错误态提供刷新；测试同时验证其他区域仍可用。
- [模块数量增加，短期导航成本上升] → 用稳定领域命名、index 公共出口和单向依赖规则控制复杂度，避免按技术类型无限细分。
- [四端无法在同一 Windows 机器完成同等级验证] → 把共享 renderer、同步、原生编译和真机验证分别报告；iOS 原生门禁放入 macOS CI/Xcode。
- [重构过程中发现非关键产品缺陷] → 记录复现证据并新建独立 OpenSpec change，不在本变更中改变用户行为。

## Migration Plan

1. 记录基线：运行现有检查，添加 API、查询键、权限和核心页面特征测试；任何基线失败先记录，不借重构扩大修复范围。
2. 建立新 API 目录：先移动类型、共享 client 和 query keys，再按领域移动函数；兼容门面继续重导出全部原符号。
3. 建立共享规则：提取纯格式化、状态映射、错误归类、脱敏和操作控制器，补齐单元测试。
4. 按低风险到高风险迁移页面领域：行情/市场、通知、购买记录、资产、订单、供应方、管理员、卡时业务。每个阶段只移动一个领域并运行相关测试。
5. 把路由收敛为 shell，为每个领域安装 Error Boundary，验证所有身份组合与未登录浏览。
6. 执行全量静态检查、单元/组件测试、Windows/Web 生产构建、Android/iOS renderer 构建和可用的原生同步/编译步骤。
7. 使用真实环境只读冒烟脚本验证登录状态、商品列表和资产读取，不执行任何写操作。

每一步形成可独立审查的提交。若某领域迁移失败，回退该领域提交并继续使用兼容门面旧实现；不需要回滚数据库或后端，因为本变更不修改二者。若发现资金、订单或敏感信息关键缺陷，先增加失败测试，再做最小修复并单独记录在交付说明中。
